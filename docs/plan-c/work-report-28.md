## 実装したこと

候補へ共通コア由来の暫定readinessを付け、生成中の設定変更候補もモデルへ残す。
順位・候補数・5→8→全候補の上限はD27と同じで、readinessによる並べ替えや除外はしない。
各段階で状態を取得し、最終提案は従来のガードと共通実行コアを通る。

引数の確定前に実行可能だと誤認させないため、値・ジョブ・履歴等が未検査の候補は
「値・参照を確認してから判定します」と表示する。既知の生成中制約はそれより優先して示す。
対象・版・観測時刻・未検査項目をDTOとして分離し、モデルには実行能力を渡さない。

画面の「候補の状態を更新」はread-only APIで現在の理由を取得する。
古い拒否結果や診断の書き換え、モデルの再推論、設定保存、生成予約はしない。
生成完了後も残る元のカードを「この依頼は実行しませんでした」と表示し、
判断時点の理由と現在の候補状態を区別した。

Hard Filterは`backend/evaluation/readiness_filter.py`の実験用関数として追加した。
既知のblocked/unsupportedを除き、引数未検査の候補と非実行・質問の余地は残す。
製品からのimportや設定による有効化はない。共通条件での方式比較はD29で行う。
仕様と導入は[candidate-readiness.md](candidate-readiness.md)を参照。
