# Plan C D34 Work Report — Explicit SQLite migration and rollback safety

## Result

D34 is complete at the automated verification gate. D35 has not started.

D34 replaces startup-time reflective mutation with a lease-bound SQLite v0-to-v1 migration. The implementation registers ORM metadata without DDL, acquires one non-blocking sibling lease before database I/O, classifies and backs up supported ancestry, migrates tables, columns, and metadata-required index sets additively, verifies the result, initializes the current schema, and retains the lease until all database users and cached connections are stopped. Migration failure keeps only the bounded startup and degraded-health APIs available; database dependencies return the fixed 503 response.

No Alembic, reverse SQL, cross-database support, public failpoint, real provider call, real user database, release, tag, publication, or deployment was added.

## Fixture ancestry and compatibility evidence

The final-review focused gate collected **121 tests**: **107 migration/restore tests** and **14 startup/lifecycle tests**.

- Frozen `upstream_v0` and `d30_v0` fixtures are explicit historical SQL and build with empty `MetaData`; they are not generated by subtracting current tables or columns.
- `empty_v0`, `upstream_v0`, `d30_v0`, `partially_additive_v0`, `current_v1`, and `newer_v2` build deterministically. Empty v0 creates v1 without backup; non-empty supported v0 migrates with a backup; v1 is verified without mutation; v2 fails `schema_too_new` without mutation.
- A registered-metadata scratch database supplies the expected table/column set, SQLite affinity, and ordered primary keys. Known identifiers use ASCII-only A--Z folding; mixed-case known identifiers migrate, distinct unknown Unicode identifiers and unknown extras survive, and ASCII-case-colliding known metadata fails before DDL.
- Exact affinity comparisons cover `INTEGER`, `TEXT`, `BLOB`, `REAL`, and `NUMERIC`. Five deliberate collisions (`projects.id`, `projects.title`, `external_calls.response_body`, `projects.progress`, and `projects.subtitle_enabled`) fail before DDL, while different declarations with equal SQLite affinity pass.
- Missing nullable/defaulted fields remain additive. A missing required known column, altered/missing legacy PK, unsupported database, negative/newer schema version, missing/released/wrong-database lease, redirected backup root, or malformed backup fails closed.
- Required ordinary and unique exact column sets are derived from `Table.indexes`, `UniqueConstraint`, and column uniqueness metadata. Quoted `PRAGMA index_list/index_info` observations use ASCII-only case folding. Unique indexes satisfy ordinary requirements on the same set; ordinary indexes do not satisfy uniqueness. Missing sets receive deterministic quoted names after additive columns exist, while existing weaker and unrelated indexes remain unchanged.
- Three partial-v0 fixtures omit `generation_artifacts.job_id`, `operation_requests.job_id`, and `language_turns.parent_request_id`. Migration restores each unique set and SQLite rejects duplicate non-null inserts. Malformed v1 fixtures missing either an ordinary or unique required set are rejected; mixed-case index columns are accepted.

## Declared and semantic reference evidence

Migration, backup, and restore require `PRAGMA foreign_key_check` to be empty and validate the explicit semantic relationships for block/job ownership, same-project parent jobs, external calls, artifact project/job ownership, settings revision ancestry, current artifact ownership, language request/turn existence, and reciprocal parent/successor links. Mixed-case test schemas execute all nine semantic-check branches. Explicit-null reciprocal links fail rather than passing through SQL three-valued logic.

Immutable `operation_requests.project_id` and nullable `job_id` remain intentional non-FKs so receipts survive deletion. Missing referenced rows remain valid; an existing job must match the receipt project, including rejection of a null owner. Language project/core IDs are durable correlation references: a deleted project is valid, while an existing core receipt requires a non-null equal project owner. Tests prove these references survive migration unchanged.

## Failure, restore, and lease evidence

Injected backup integrity/hash, DDL, post-migration identity, post-migration reference, lease-loss-before-backup-publication, and lease-loss-before-metadata-publication failures retain no incomplete pair. A verified backup remains available after DDL or post-verification failure. The stable reason-code set is:

`database_lease_unavailable`, `schema_too_new`, `unsupported_database`, `unsupported_legacy_schema`, `backup_failed`, `backup_invalid`, `migration_failed`, and `migration_verification_failed`.

Offline restore acquires the same lease itself without waiting and releases it in `finally`. Before target mutation it rejects modified/corrupt bytes, wrong-target binding, escaping paths, symlinks, special files, Windows reparse points, noncanonical/unsupported metadata, incomplete v1 schema, identity mismatch, and semantic-reference mismatch. Only after full validation does it reassert ownership before deleting each stale `-wal`, `-shm`, and `-journal`, replace atomically, fsync, reopen, and reverify hash, integrity, schema, identities, and references. A spawned live application excludes restore immediately with unchanged target and backup bytes; the same restore succeeds after application shutdown.

The lease file is `<database>.migration.lock`, created once with exclusive creation and no polling, retry, or stale cleanup. Its canonical PID/UTC/random-token payload, descriptor/path identity, and exact bytes are checked on assertion and release. In-place tamper fails. Release uses an owner tombstone and never deletes a replacement owner; forced replacement/collision tests prove restore-or-retain behavior. A stale lease may be removed only after an operator confirms that no application or restore process is live.

## Application lifetime and degraded API evidence

Lifespan order is exact: `register_models()`, acquire lease, `migrate_database(..., lease=lease)`, `init_db()`, ready state, recovery, registry, dispatcher. Ready and migration-degraded processes retain the same lease. Shutdown closes registry admission, stops dispatcher work, drains the registry, publishes a non-ready state, disposes and clears the cached engine/sessionmaker without DDL, then releases the lease exactly once as the final database lifecycle action. Post-acquisition startup errors use the same cleanup; acquisition failure starts no database user and attempts no release. App/app and app/restore spawned-process tests prove immediate exclusion. A restore between two lifespans proves the second lifespan opens restored bytes through a fresh pool rather than the replaced inode.

`GET /api/startup` remains 200. Migration failure makes `GET /api/health` degraded. Database routes return 503 with `Retry-After: 5` and only `startup_unavailable` plus the fixed Japanese message; raw database, backup, and lease paths are not exposed. All eight migration reason codes are covered. Recovery and dispatcher startup are skipped in degraded state.
