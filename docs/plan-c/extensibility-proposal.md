# BlockVideo 拡張性改修提案書 — 小さなモデルで大きなシステムを動かし、確認なしで完成品まで届ける

- 作成日: 2026-10-06（同日改訂: YOLO モードを追加）
- 作成: Claude（実装エージェント）
- 位置付け: 提案。第 2 章の承認・決定済み事項以外は、まだ承認されていません。
- 前提: コスト（モデル呼び出し回数、評価の計算量、開発工数）は度外視します。応答時間と安全性は制約として残します。

## 0. 要旨

この提案は 2 つのことを目指します。

- **拡張性**: RAG で操作を検索し、ごく小さなモデル（1〜3B パラメータ級、文脈 4,000 トークン程度）でも、数百〜数千の操作を持つ大きなシステムを安全に操作できるようにします。
- **速さ**: 画面で選べる **YOLO モード**を用意します。自然文の入力から完成した動画の手渡しまで、人の確認を一切挟まずに進めます。足りない値は推測して進めます。

そのための方針は 4 つです。

1. **知識はモデルではなくカタログに置く**: 操作・引数・値の根拠と推測規則・安全区分・手順のひな形・画面表示・評価の基準を、検索できるカタログに一本化します。プロンプト、文法、画面、評価はカタログから自動生成します。
2. **モデルの仕事を「小さな選択問題」に分解する**: 1 回の呼び出しでは「5 択から 1 つ選ぶ」「引数を 1 つ埋める」程度だけを任せます。それ以外は決定論的な処理と検証に任せます。
3. **計画と実行を分ける**: 複数手順の依頼は「計画（手順の列と依存関係）」として扱います。各手順は、今ある安全装置と実行直前の再確認をそのまま通します。
4. **人の確認は方針で外せるようにする**: 通常モードでは今の確認を保ちます。YOLO モードでは、確認と聞き返しを「自動の判定と推測」に置き換えます。その代わり、何をしたか・何を推測したかを完成品と一緒に報告し、ワンクリックで元に戻せるようにします。

進め方は 7 段階です（第 6 章）。最初の段階は「測定の信頼回復」です。D35.1 の held-out 結果が正解率 15.7%／18.5% と異常に低く、採点側に製品とのずれが残っている疑いがあります。改修の効果を測れる状態にすることが、全段階の前提です。YOLO モードの第 1 版は、カタログの一本化の直後（段階 2）に入れます。

## 4. 目標アーキテクチャ

### 4-1. 設計原則

1. **モデルは提案するだけ**: 状態を変えるのは登録済みハンドラだけです（現行を維持）。
2. **知識はカタログに一本化する**: 操作についての知識を、コードや画面や評価に重複して書きません。
3. **1 回の呼び出しは小さな選択問題にする**: 選択肢は 5 件程度まで、出力は数十トークンまでにします。
4. **決定論的にできることは決定論的に**: 数値と単位の抽出、正規化、参照番号の照合、検証はコードで行います。
5. **出力は必ず文法で縛り、検証する**: 不合格のとき、通常モードは聞き返し、YOLO モードは推測規則で補います。
6. **計画と実行を分ける**: 手順ごとに安全装置を通します。
7. **人の確認は方針で外せる。自動の安全検査は外せない**: YOLO モードで省くのは人を待つ場所（3-2 の W1〜W6）だけです。
8. **段階ごとに測る**: 検索・選択・引数・推測・計画・最終結果を別々に採点し、どこで落ちたかを分かるようにします。

### 4-2. 全体図

```text
 依頼文（＋モード: 通常 / YOLO）
   │
   ▼
 ① 正規化・決定論的抽出（数値+単位, 否定, 参照番号, 日付）◀── カタログの「根拠仕様」
   │
   ▼
 ② 階層型検索（領域 → 機能 → 操作 / 手順ひな形）
   │  語句一致 + 埋め込み + 再順位付け + 同義語、上位を複数残す
   ▼
 ③ 選択（小さなモデル: 5 択から 1 つ、複数回の多数決）
   │  確信が足りない ─┬─ 通常: 確認質問
   │                  └─ YOLO: 推測の段階（4-3 I）で最有力を採用し、推測として記録
   ▼
 ④ 計画の組み立て（単発 → 1 手順の計画 / 複数手順 → 手順ひな形を選んで穴を埋める）
   │  対応外の部分 ─┬─ 通常: 全体を止める
   │                └─ YOLO: 実行できる部分だけ進め、残りを報告（第 8 章で判断）
   ▼
 ⑤ 引数の充填（引数 1 つずつ、型ごとの文法で縛る）
   │  ①で抽出した値を優先 / 状態の候補（ジョブ一覧など）から選ばせる
   │  値が無い ─┬─ 通常: 確認質問
   │            └─ YOLO: カタログの推測規則 → 状態の候補 → モデルの最有力（範囲内）
   ▼
 ⑥ 自動の安全検査（両モード共通・外せない）
   │  スキーマ・許容範囲・明示された指示との矛盾なし・安全方針・前提条件・計画の整合・上限
   │  不合格 ─┬─ 通常: 確認質問
   │          └─ YOLO: その部分は実行せず、報告に回す
   ▼
 ⑦ 計画の提示と確認 ─┬─ 通常: カタログの文言から機械的に作文して見せ、確認を待つ
   │                  └─ YOLO: 省略（記録だけ残す）
   ▼
 ⑧ 手順ごとの実行: 実行直前の再確認 → 登録済みハンドラ
   │  状態が変わっていた ─┬─ 通常: 止める
   │                      └─ YOLO: 最新の状態で解釈し直して再計画（回数に上限）
   │  生成ジョブ ─┬─ 通常: 生成の確認を待つ
   │              └─ YOLO: 自動で開始し、完了まで待つ。失敗は上限回数まで自動で再試行
   ▼
 ⑨ 完成品の手渡し（YOLO）: 完成した動画 + 報告（実行したこと / 推測したこと と根拠 / 飛ばした部分 / 時間・費用）
   │  [元に戻す] ボタン: 設定の版と、前の成果物に戻す
   ▼
 ⑩ 記録と観測（検索の取りこぼし、質問・推測の発生、失敗の種類）──▶ カタログ改善へ
```

### 4-3. 構成要素ごとの提案

#### A. カタログを唯一の情報源にする（カタログコンパイラ）

操作ごとに次の情報をカタログに持たせ、検証してから各所に配ります。

| カタログの項目 | 今の置き場所 | 生成・利用先 |
|---|---|---|
| 引数の型・説明・例 | definitions.json | 応答の文法、プロンプト、画面のフォーム |
| 安全区分・確認の要否・否定語・参照の種類 | operation_policies.json（D35.2） | 安全装置、通常モードの確認、画面の確認ダイアログ |
| モデル向けの規則と例（モード別） | prompt_rules.json（D35.2） | プロンプト。規則に「通常のみ」「YOLO のみ」の印を足す |
| 引数の根拠仕様（単位、同義語、相対変更の刻み、聞き返しの文） | subtitle_values.py などの正規表現 | ①の抽出と⑥の検証（新設） |
| 引数の推測規則（YOLO 用。量の無い「大きく」の既定の刻み、既定値、推測の許容範囲） | 無し | ⑤の推測（新設） |
| 前提条件・事後条件・ハンドラの対応 | bootstrap.py、catalog.py の閉じた一覧 | 実行可否の判定（ハンドラ側の宣言と照合） |
| 状態の見え方（その操作の判断に要る状態） | 無し（4 項目固定） | ⑤の状態候補（新設） |
| 補償操作（取り消し方） | 無し | ⑨の「元に戻す」、⑧の失敗時（新設） |
| YOLO での扱い（自動実行の可否、費用の重み） | 無し | YOLO の上限管理（新設） |
| 画面表示（表示名、結果の見せ方） | フロントエンドの直書き | 画面（バックエンドが配布） |
| 評価の基準（設定一覧、操作一覧、等価な書き方、推測の許容範囲） | 評価ツールの直書き | 評価・採点 |

**カタログコンパイラ**は、これらを読み、矛盾（方針の無い操作、未定義の参照種別、文法にできない型、推測規則の無い必須引数など）があれば起動も評価も止めます。検索インデックスもここから作り直し、インデックスとカタログの版を結び付けます。

#### B. 階層型・混合型の検索

- **階層**: 操作を「領域（動画・字幕・音声…）→ 機能 → 操作」の木に整理します。各段で上位数件だけを次に渡すので、操作が 1 万件でも、1 回にモデルへ見せるのは 5 件程度で済みます。
- **混合検索**: 埋め込みに加えて、語句一致（BM25 など）と同義語辞書を使います。日本語の言い換えや設定名の揺れに強くするためです。
- **再順位付け**: 小さな再順位付けモデル（cross-encoder など）で上位を並べ替えます。
- **ビーム**: 各段で 1 件に決め打ちせず、上位 3 件ほどを残して、最後に検証で絞ります。階層を重ねたときの取りこぼしの連鎖を防ぎます。
- **例文の検索**: 固定の例を全部載せるのをやめ、依頼に近い例だけを検索して載せます。
- **長い対話への対応**: 検索文を「今回の依頼」と「保留中の意図」に分け、上限超過で検索自体を飛ばす今の挙動をやめます。

#### C. 小さなモデル向けの「微小決定」

| 決定 | モデルへの問い | 出力の縛り |
|---|---|---|
| 操作の選択 | 「次の 5 件のうち、依頼に合うのはどれか。無ければ none」 | 列挙型 1 つ |
| 引数の充填 | 「引数 X の値は何か。依頼に無ければ missing」 | X の型の文法 |
| 肯定・否定 | 「この操作を頼んでいるか、頼んでいないか」 | 列挙型 1 つ |
| 状態の候補選択 | 「対象のジョブは次のどれか」 | 候補 ID の列挙型 |
| 推測（YOLO） | 「X が書かれていない。次の候補のうち最もありそうなのはどれか」 | 許容範囲内の候補の列挙型 |

- **多数決**: 1 つの問いを複数回（例えば 5 回、温度を少し上げて）解かせます。通常モードでは一致率が基準未満なら確認質問にします。YOLO モードでは最多の答えを採用し、一致率を推測の確信度として報告に載せます。
- **検証役**: 別の呼び出しで「この選択・推測は依頼の明示された内容と矛盾しないか」を判定させます。矛盾するものは、どちらのモードでも採用しません。
- **決定論的な抽出が先**: 「64px」「1.2 倍」「ジョブ 7」のように、根拠仕様で抜き出せる値はコードで抜きます。モデルには、抜けた値をどの引数に入れるかだけを選ばせます。

#### D. 状態の検索と候補化

- 操作ごとに「判断に要る状態」をカタログで宣言します（例: キャンセルなら実行中のジョブ一覧、版を戻すなら設定履歴の一覧）。
- モデルには ID を生成させず、状態から作った候補一覧から選ばせます。今の「参照番号が依頼文に明示されているか」の点検は、候補選択と照合に置き換えます。
- YOLO モードの推測でも、この候補を使います（例: 「再試行して」だけなら直近の失敗ジョブ、「前の設定に戻して」だけなら 1 つ前の版）。
- 状態は必要な分だけ検索して渡し、「選択中プロジェクトの 4 項目だけ」をやめます。

#### E. 計画と実行の分離

計画の契約（案）です。

```json
{
  "plan": {
    "recipe": "save_then_generate",
    "steps": [
      {"id": "s1", "operation_id": "project.settings.update", "operation_version": 1,
       "arguments": {"subtitle_font_size": 64}, "depends_on": []},
      {"id": "s2", "operation_id": "project.generation.start", "operation_version": 1,
       "arguments": {"kind": "full"}, "depends_on": ["s1"],
       "inputs": {"base_revision": {"from": "s1.result.revision"}}}
    ],
    "guesses": [
      {"step": "s1", "argument": "subtitle_font_size", "value": 64,
       "basis": "「大きく」に既定の刻み +16px を適用（推測規則）", "agreement": "4/5"}
    ]
  }
}
```

- **今の動きはすべて計画で表せます**: 単発の依頼は 1 手順の計画です。「保存してから生成」は 2 手順のレシピになり、`generate_after_save` と専用処理（generation_followup.py）は不要になります。
- **推測の記録**: 推測した値は、根拠と確信度とともに計画に残します。通常モードでは推測は起きません。
- **レシピ**: よくある複数手順を、引数の穴が空いたひな形としてカタログに書きます。小さなモデルには、自由に計画を作らせず、レシピを選んで穴を埋めさせます。
- **手順間の値の受け渡し**: 前の手順の「記録された結果」（受領記録）だけを参照できます。モデルの出力を次の手順に直接流しません。
- **確認**: 通常モードでは計画全体を一度見せ、方針で確認が必要な手順はさらに個別に確認します。YOLO モードでは確認を省きます（I を参照）。
- **失敗時**: その手順で止め、残りは実行しません。カタログに補償操作があれば、元に戻す提案を出します。
- **既存の仕組みの再利用**: 二重実行の防止、確認トークン、実行直前の版の再確認は、手順ごとにそのまま使います。YOLO モードでは、確認トークンをサーバー内部で発行・消費します。

#### F. 安全装置の宣言化

- D35.2 で作った方針ファイルを、引数ごとの根拠仕様と推測規則まで広げます。今の正規表現による検査（字幕サイズ・話速）を、根拠仕様から自動生成される検査に置き換えます。
- 方針の無い操作は起動時に拒否し、万一呼ばれても「変更系・確認必須」として扱います（D35.2 で導入済み）。YOLO モードでも、方針の無い操作は自動実行しません。
- 計画全体に対する検査を加えます。依存関係の循環、確認の抜け、同じ対象への矛盾する変更などです。

#### G. 文脈予算とモデルの抽象化

- **トークン数の実測**: モデルごとのトークナイザーで実測し、「文脈 − 出力 − 余裕」に収まるように候補数・例文数・状態の量を自動で調整します。
- **モデルの能力記述**: 文脈長、文法制約に対応しているか、トークナイザーを記述し、微小決定ごとに使うモデルを選べるようにします。
- **キャッシュ**: 共通部分（規則・形式の指示）を前置きに固定し、プレフィックスキャッシュを効かせて呼び出し回数の増加による遅延を抑えます。
- **並列化**: 互いに独立な問い（引数ごとの充填、多数決の各回）は並列に呼びます。YOLO モードの速さに直結します。
- **上限の見直し**: 呼び出し回数と時間の上限（4 回・180 秒）を「依頼全体の時間予算」に置き換えます。

#### H. 観測と改善ループ

- 検索の取りこぼし、確認質問・推測の発生、検証での却下、YOLO での「元に戻す」の使用を記録します。依頼文そのものは記録せず、分類と ID だけを残します。
- 取りこぼしや外れた推測が多い言い回しは、同義語・例文・推測規則としてカタログに追加し、開発用問題で回帰を確かめてから反映します。

#### I. YOLO モード（確認なしで完成品まで）

**切り替え**

- 画面の自然文入力欄に「確認なしで最後まで実行（YOLO）」の切り替えを置きます。既定はオフです。
- オンにすると入力欄に目立つ表示を出し、最初にオンにしたときだけ、何が自動になるかの説明を表示します。依頼ごとの確認ではありません。
- 設定は利用者ごとにサーバー側で保存します。依頼には `mode: "yolo"` を付けて送ります。
- サーバー側の設定で YOLO モード自体を無効にできるようにします。評価で基準を満たすまでは無効にしておきます（5-5）。

**省くもの・残すもの**

| 区分 | 内容 |
|---|---|
| 省く（人を待つ場所） | 値が足りない・あいまいなときの聞き返し（W1）、生成・再試行の確認（W2）、保存後の生成の確認（W3）、計画の提示と確認、生成完了の手動確認（W6） |
| 自動判定に置き換える | 対応外が混ざった依頼（W4）→ 実行できる部分だけ進める。実行直前の状態変化（W5）→ 最新の状態で再計画 |
| 外さない（自動の安全検査） | 登録済みハンドラだけが状態を変える／明示された指示（「生成しないで」「戻さないで」など）に反しない／スキーマと許容範囲／方針の無い操作は実行しない／二重実行の防止／秘密情報の保護／時間・回数・費用の上限 |

**推測の段階（値が足りないとき）**

1. 依頼文と会話から決定論的に抜き出せる値を使う。
2. カタログの推測規則を使う（例: 量の無い「大きく」は既定の刻み幅、話速の指定が無ければ現在値のまま）。
3. 状態の候補から選ぶ（直近の失敗ジョブ、1 つ前の版、選択中のプロジェクトなど）。
4. 小さなモデルの多数決で、許容範囲内の候補から最有力を選ぶ。
5. 検証役が「明示された内容と矛盾しない」と判定したものだけを採用する。
6. どれでも決まらない部分（対応外の機能など）は実行せず、報告に回す。

推測した値は、根拠と確信度とともに必ず報告に載せます。発音の読み方のように、今は「推測しない」と決めている項目も、YOLO モードでは推測の対象になります（読み方は一般的な読みを採用し、報告に載せる）。

**最後まで自動で進める**

- 計画の手順を順に実行し、生成ジョブは自動で開始して完了まで待ちます。
- 生成が失敗したら、上限回数（例: 2 回）まで自動で再試行します。
- 実行直前に状態が変わっていたら、最新の状態で解釈し直して再計画します（上限回数あり）。
- 上限（依頼全体の時間、生成の回数、有料 API の費用）に達したら、そこで止めて報告します。生成には、利用者が持ち込んだ LLM・画像の API キーを使う外部サービスが含まれ得るため、費用の上限は必須です。

**完成品の手渡しと事後の取り消し**

- 完成した動画を画面に表示し、ダウンロードできる状態にします。
- 報告には次を載せます: 実行した操作、推測した値と根拠、飛ばした部分と理由、かかった時間と費用。
- 「元に戻す」ボタンで、設定を依頼前の版に戻し、前の成果物を現在の成果物に戻します。設定の版を戻す操作は既にあります。成果物を戻す操作は新設が必要です。人の事前確認の代わりに、事後に確実に戻せることで安全を担保します。

**速さ**

- 人を待つ時間が無くなることが一番の効果です。
- 解釈側は、独立した問いの並列化とプレフィックスキャッシュで、呼び出し回数の増加を相殺します。
- 生成側の高速化案です（任意）: 変更の影響を受けるブロックだけ作り直す、ブロックごとの音声合成を並列化する、動画の書き出しに GPU を使う。

## 5. 評価とリリース判定の改修

### 5-1. 段階別の指標

| 段階 | 指標 | 目標案 |
|---|---|---|
| 検索 | 正解の操作が上位 5 件に入る割合（recall@5） | 98% 以上 |
| 選択 | 正しい操作または正しい「質問すべき」の判断 | 95% 以上 |
| 引数 | 引数ごとの完全一致 | 95% 以上 |
| 計画 | 手順と依存関係の一致 | 90% 以上 |
| 最終結果 | 状態の変化が期待どおり（今の task_complete） | 90% 以上・各分類 80% 以上（現行の基準） |
| 安全 | 許可していない変更・二重実行・漏えい | 0 件（現行の基準） |

目標値は提案です。段階 0 で測定が信頼できる状態になってから、実測をもとに決め直します。

### 5-2. YOLO モードの指標

| 指標 | 内容 | 目標案 |
|---|---|---|
| 完走率 | 止まらずに完成品まで届いた割合 | 90% 以上 |
| 推測の妥当率 | 推測した値が、問題に書いた「許容される推測」の範囲に入った割合 | 85% 以上 |
| 明示指示への違反 | 明示された指示に反する実行 | 0 件 |
| 安全 | 許可していない変更（推測の許容範囲外を含む）・二重実行・漏えい | 0 件 |
| 取り消しの成功 | 「元に戻す」で依頼前の状態に戻った割合 | 100% |
| 所要時間 | 依頼から完成品までの時間（偽のプロバイダで測る） | 実測後に決める |

推測を採点するには、問題に「許容される推測」（値の範囲や候補）を書き足す必要があります。held-out 問題への追加は、これまでと同じく人と独立 AI の承認を経ます。

### 5-3. 採点の信頼性

- **実製品での照合を必須にする**: 新しい操作やイベントを足すときは、実際の製品で採点し、正しい振る舞いが「完全に正解」になることを確かめるテストを必須にします（2026-10-05 に、全イベント種別を含む流れで導入済み）。YOLO モードの流れも同じように追加します。
- **状態差分による採点**: 「許容される提案」の手書き列挙（限界 8）をやめ、実行前後の状態差分を期待値と比べます。同じ意味の書き方（set と adjust、v1 と v2 など）を作問者が全部並べなくて済むようにします。
- **評価の契約をカタログから作る**: 設定一覧・操作一覧をカタログから生成します（限界 6）。
- **規則の改訂**: `evaluation/d24/RULES.md` の「推測しない」系の規則は通常モード用と明記し、YOLO モード用の規則（推測してよい範囲、報告の義務）を加えます。

### 5-4. 新しい問題形式と試験

- **複数手順の問題形式**: 手順の列、手順ごとの期待効果、途中失敗のときの期待挙動を書ける形式にします（限界 7）。
- **規模の試験**: 合成カタログ（1,000 件・10,000 件。似た名前の紛らわしい操作を含む）で、検索の取りこぼし、確認質問・推測の率、応答時間を測ります。
- **モデルの段階試験**: 0.5B・1.5B・3B・7B・27B 級のモデルで同じ試験を行い、どの大きさから合格するかを記録します。
- **微調整（任意）**: カタログから合成した練習問題で小さなモデルを微調整する案です。held-out を学習に混ぜないよう、データの出所を記録します。

### 5-5. リリース判定（D40）の変更

| 項目 | 現行 | 変更後 |
|---|---|---|
| 既定モード | All Tools（RAG が同等以上なら RAG） | RAG を常に既定にする（承認済み） |
| RAG の条件 | 全問実行・正解率・各分類・安全 | 同じ（必須） |
| All Tools の条件 | 上記すべて必須 | 実行完了と安全は必須。正解率の 2 条件は参考値（観測値は記録に残す） |
| YOLO モード | 無し | 第 3 のモードとして評価する。5-2 の基準を満たした場合だけ、画面の切り替えを有効にして出荷する |
| 追加する条件（案） | — | 検索の recall@5、規模の試験、指定した小さなモデルでの合格 |

All Tools の安全を必須のまま残すのは、RAG も検索で見つからないときは全操作の段階に広げるためです。All Tools の安全性は、RAG の安全性の一部です。

### 5-6. 評価基盤

- **並列化**: 1 試行の時間の内訳（モデル推論、試験ホストの起動、DB の準備）を測ってから決めます。試行ごとの隔離と、中断からの再開は維持します。
- **カーネル領域の増加**: 試行のたびにカーネル領域が増える現象の原因を特定します。1 試行あたり、ページング可能な領域が約 0.022 GiB、ページング不可の領域が約 0.008 GiB 増えています。LM Studio だけ、試験ホストだけ、をそれぞれ繰り返して切り分けます。製品側が原因なら利用者の環境でも長時間の利用でメモリが減っていきます。YOLO モードは連続して自動実行するので、なおさら事前に確かめる必要があります。

## 7. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 採点のずれが残ったまま改修を進める | 改修の良し悪しを判断できない | 段階 0 を最優先にする。実製品での照合テストを必須にする |
| YOLO で外れた推測がそのまま実行される | 意図と違う設定・動画ができる | 推測の段階と検証役。推測を必ず報告する。「元に戻す」で確実に戻せるようにする。外れやすい言い回しを推測規則に反映する |
| YOLO で費用が膨らむ | 有料 API の請求が増える | 依頼ごと・期間ごとの費用上限、生成回数と再試行の上限。上限に達したら止めて報告する |
| YOLO の自動再計画・再試行が繰り返される | 時間とリソースを使い続ける | すべての自動の繰り返しに回数と時間の上限を設ける |
