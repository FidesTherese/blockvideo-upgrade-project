# D17 実装・検証報告

## 結果と合意した方針

D17のAll Tools方式を実装した。検索を使わず全8操作の定義をローカルモデルへ渡し、
自然言語の解釈から既存の共通操作コア、永続化された実行結果まで接続する。
原文の計画書にある人間の確認欄は変更していない。

今回の対話で次を確認した。

- 設定変更は即時保存。動画生成・再試行は、対象と内容を別途確認してから開始する。
- 変更量が曖昧なら聞き返す。従来の「少し＝2px」の規則は維持する。
- 使用者ごとに言い方が異なるため、人間に一つの固定例文を要求せず、複数の合成表現をこちらで用意する。
- 例文をベクトル化して類似度で操作へ振り分ける案は議論した。D17の検索なし方式には混ぜず、
  後段で比較できる案として扱う。類似度による候補選択の後にも、数値・否定・対象などの検証が必要。

自然言語用の通常画面・結果カードはD18、質問への回答を引き継ぐ対話はD19の範囲。
この報告では、新しい画面を作ったとは主張しない。

## 実装した流れ

1. クライアントは要求ID、文章、選択中のプロジェクトIDを送る。
2. 既存要求を最初に照会する。同じID・同じ内容なら、保存済みの結果を返す。
3. 新規要求では、対象と現在の設定revisionをアプリが固定する。
4. モデルに全操作の定義と最小限の状態を渡す。原稿・動画・タイトル・履歴全体・秘密情報を状態から送らない。
5. JSON全体、操作IDと版、引数の型・範囲を検証する。対象、要求ID、revision、生成許可はモデルに決めさせない。
6. ジョブ・履歴の番号は、文章中の明示的な番号とも一致することを確認する。モデルの推測値では実行しない。
7. 確定要求を保存し、既存の操作コアで現在の状態とrevisionを再検証して実行する。
8. 保存値・ジョブID・確定結果を返す。モデルが自由文で「できました」と言ったことを成功扱いしない。

`app.interpretation` はD16の読取り専用境界のまま。
新しい `app.language_operations` が接続を担当し、`routes_language.py` がHTTP入口を提供する。
新規の `language_requests` テーブルには原文専用フィールドを置かず、入力のハッシュ、対象、版、
構造化された解釈、確定要求、結果参照を保存する。構造化引数やモデルの質問文自体は記録される。
実行の正本は従来の操作コアのreceiptで、要求本文が一致するreceiptだけを復旧に使う。

同時送信で解釈する所有者は一つ。推論中はDBの書込みロックを保持しない。
推論が中断して210秒の期限を超えた場合は、自動推論を繰り返さずエラーを返す。
コアの確定後、自然言語側の応答保存前にプロセスが終了しても、receiptから元の結果へ戻れる。

## 開発用API

| 入口 | 用途 |
|---|---|
| `POST /api/language/requests` | 解釈し、確認不要の操作を実行する |
| `POST /api/language/requests/prepare` | 設定を書き換えず、解釈と確定要求を確認する |
| `GET /api/language/requests/{request_id}` | モデルへ接続せず、保存済みの状態を取得する |
| `POST /api/language/requests/{request_id}/execute` | 保存した提案を確認して実行する |

字幕変更の入力例。プロジェクトIDは実際に選択した対象を指定する。

```json
{
  "request_id": "subtitle-change-001",
  "text": "字幕を56pxにして",
  "target": {"selected_project_id": 1},
  "base_revision": 1
}
```

`base_revision` は省略時にアプリが現行値を記録する。画面が認識している版を送れば、
既に古い画面からの変更も解釈前に拒否できる。

生成の提案は `ready` と `requires_confirmation: true` を返す。
対象と `prepared_request` を表示し、利用者が開始した場合だけ、返されたトークンで確認する。

```json
{
  "confirmation_token": "prepareまたはsubmitで返された64文字のトークン",
  "confirm_generation": true
}
```

確認時に操作名・引数・対象を差し替えることはできない。
`completed` は「操作コアの処理が確定した」という意味であり、生成要求ではジョブの受付完了を表す。
動画の完成は別途ジョブと成果物履歴で確認する。

不足・未対応・blocked・エラー後に内容を訂正する場合は、新しい要求IDを使う。
同じIDの再送で本文を変えると409になる。JSON形式の不正は原文を反射せず固定の422エラーを返す。

別内容のコアreceiptの誤採用防止、異常Unicodeの安全な拒否など。

実際に別Pythonプロセスを終了させる試験を、解釈保存後とコア確定後の2か所で実施した。
再送で再推論・相対値の二重加算・二重ジョブが起きないことを確認した。
既知のStarlette/httpx非推奨警告が1件ある。新たな依存ライブラリは追加していない。

## 実モデルで見つけた失敗と修正

Ternary Bonsaiに全8操作を渡すと、最初は値不足を「未対応」と判定した。
値不足の例だけ追加すると、今度は「少し大きく」の既定値まで不足と判定した。
絶対値・相対値・値不足を対にした説明で、代表7要求が通るようになった。

表現を27件に広げた初回は23/27件だった。

| 再現入力 | 初回の問題 | 対処 |
|---|---|---|
| 字幕をもっと読みやすくしたい | 未対応に分類 | 不足と未対応を区別する説明を補強 |
| 字幕を大きくしてから動画も作り直して | 生成だけを提案 | 複数操作の一部を落とさず質問する説明を補強 |
| 生成をキャンセルして | 未対応に分類 | job_id不足を質問する説明と参照検証 |
| 以前の設定に戻して | 現在のrevisionを推測で使用 | 戻す版を質問する説明とアプリ側の参照検証 |

修正後の27/27は開発用ケースでの結果であり、未見の文章での精度や研究上の優位性ではない。
プロンプト修正に使ったケースを独立した最終評価データとして扱ってはいけない。
形式が正しいモデル出力でも、意味を誤る可能性は残る。構造化提案を記録し、
不明な参照は止め、生成には文章とは別の確認を要求する。

初期の失敗は `initial-classification-failure.json`、`second-classification-failure.json`、
`initial-wording-variants.json` に保存している。成功した結果だけに置き換えていない。

## 残る範囲

自然言語UIはD18、対話の文脈保持・訂正・対象切替はD19。
現在は画面やAPIから対象IDを明示する。別名や「前の動画」の自動特定はしない。
ジョブ・設定履歴の番号が明示されない場合は質問し、続きは新しい要求として送る。
単一バックエンド・単一利用者の既存構成であり、ユーザーごとの権限制御を追加したものではない。
大量プリセットの意味検索は未導入。検索を追加しても共通コアの検証と生成確認は維持する。
